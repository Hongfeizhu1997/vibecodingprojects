# IDG E-com B2C vs ISG B2B — 方案对比分析

> 基于 `idg-ecom-b2c-v2-analysis.md` 和 `product-pricing-recommendation-v3.md`
> 创建：2026-07-17

---

## 一、方案特征提炼

### IDG E-com B2C：算法驱动 · 系统内编码

```
ServicePrice = Base3YBandPrice × TermFactor × TierFactor × αγ修正

                    ┌──────────────────────────────┐
                    │     全部在系统内自动计算        │
                    │                              │
  HW AUR ──→ Band(A-J) ──→ Base3YBandPrice        │
                              ×                    │
  Term ──→ ln(Term) ──→ TermFactor                │
                              ×                    │
  Tier ──→ TierFactor (0.55~1.40)                  │
                              ×                    │
  Term>3 ──→ α(成本上升) + γ(尾部风险)              │
                              =                    │
                          ServicePrice             │
                    └──────────────────────────────┘
```

**特征**：
- 定价逻辑**完全显式编码**在系统中——Band 定义、期限曲线、Tier 倍数、成本修正都有明确的数学表达
- 每季度自动校准：重新分桶 → 更新锚值 → 重算全量 SKU
- Attach Rate 闭环反馈 → AI 自动微调系数
- 系统记录的是**推导过程**，不是结果

### ISG B2B：PenRate 驱动 · 系统外维护

```
ServicePrice = HWPrice × PenRate

    系统内              系统外（人维护）
    ──────              ────────────────
    HWPrice ──→ × ──→ ServicePrice
    
                   ↑
              PenRate ← 人在 Excel 里综合判断：
                         • GEO 是哪里？
                         • 客户段是什么？
                         • Charge Type 是什么？
                         • 竞品价多少？
                         • 历史成交价多少？
                         • Margin 底线多少？
                         → 定一个数字
```

**特征**：
- 定价逻辑**压缩成一个数字**（PenRate），系统只做乘法和查表
- 所有判断复杂度转移到线下——GEO × 客户段 × Charge Type × 竞品 × 历史 全部由人综合
- PenRate 表需要人工维护和更新
- 系统记录的是**结果**，不是过程

## 二、共同之处

| 共同点 | IDG E-com B2C | ISG B2B |
|--------|:---:|:---:|
| **核心原则** | 服务价格 = f(硬件价值) | 服务价格 = f(硬件价值) |
| **定价锚点** | HW AUR Band → Base Price | HWPrice → PenRate |
| **防利润侵蚀** | Floors/Caps (% of HW AUR) + αγ 成本修正 | PenRate 维护时人为考虑 Margin |
| **业务领域** | SSG GPS 服务 PN 定价 | SSG GPS 服务 PN 定价 |
| **与 List Price 关系** | 不依赖 List Price（独立定价） | 不依赖 List Price（独立定价） |
| **输出给销售** | 推荐售价（B2C 直接展示） | 推荐售价（B2B 商机报价） |

> 两个方案的**起点相同**——都源自"服务价格不应与硬件价格脱钩"这个基本认知。但实现这个目标的方式截然不同。

---

## 三、不同之处

| 维度 | IDG E-com B2C（算法驱动） | ISG B2B（PenRate 驱动） |
|------|------|------|
| **公式复杂度** | 4 层相乘（Band × Term × Tier × αγ） | 1 层相乘（HWPrice × PenRate） |
| **定价粒度** | 细：10 Band × 4 Tier × 5 Term = 200 个价格点 | 粗：1 个 PenRate 覆盖整个 PN/GEO/客群组合 |
| **透明度** | 高——每个因子独立可见、可审计 | 低——PenRate 在系统视角是一个 black box |
| **维护方式** | 算法自动校准（季度）+ AI 闭环调优 | 人工维护 PenRate 表 |
| **可扩展性** | 新 SKU 自动落入 Band → 自动出价 | 新 SKU → 人判断 → 人填表 |
| **一致性** | 同 HW 同价（算法保证） | 依赖人的判断，有主观差异风险 |
| **行为经济学** | 内建（对数递减感知价值） | 无（隐含在 PenRate 选择中） |
| **风控机制** | 显式 Floor/Cap (% of HW AUR) + αγ 底线 | 隐式（人在定 PenRate 时考虑） |
| **数据依赖** | 需要 HW AUR 分布历史 + Attach Rate 数据 | 需要成交价格历史 + 竞品信息 |
| **决策速度** | 实时（电商页面加载时计算） | 天级（商机报价前查表） |
| **适用场景** | B2C 电商：大流量、低接触、标准 SKU | B2B 商机：小流量、高接触、定制化交易 |

## 四、Pros & Cons

### IDG E-com B2C

#### ✅ Pros

| 优势 | 说明 |
|------|------|
| **规模化友好** | 10 个 Band 管住所有 SKU，新品自动定价，零人工介入 |
| **一致性保证** | 同一个 Band 的 HW 永远出同一个服务价格——消除人工判断差异 |
| **可解释性** | 每个因子都可追溯——"为什么这个 PS 3Y 是 $280？因为 Band E + Term 3Y = 1.25 × PS = 1.00" |
| **自我进化** | 季度校准 + Attach Rate 闭环 → 模型自动适应市场变化 |
| **低运营成本** | 上线后人工维护量 ≈ 0（仅需 Finance 季度审阅） |
| **天然风控** | α 和 γ 防止长期限 PSP 亏损；Floor/Cap 防止价格过度漂移 |
| **行为科学支撑** | 对数曲线有学术依据（时间偏好递减），不是拍脑袋定的 |

#### ❌ Cons

| 劣势 | 说明 |
|------|------|
| **冷启动成本高** | 需要 HW AUR 分布数据 + 定义 Band 边界 + 确定锚值 + 标定 α/γ——前期工作量大 |
| **Banding 刚性** | Band 边界固定，边界附近的 HW（如 AUR $1,299 vs $1,301 落入不同 Band）可能出现价格跳动 |
| **不适合谈判场景** | B2C 电商天然不需要谈判，但如果放到 B2B 场景，算法价格没有商量的空间——"系统说这个价就是这价" |
| **对数据质量敏感** | HW AUR 数据不准 → Band 分桶不准 → 锚值偏差 → 整个定价表失真 |
| **α/γ 参数需要领域知识** | 不是纯数据驱动——需要 Service Delivery 团队提供成本曲线验证 |
| **不支持捆绑/打包定价** | 每个服务 PN 独立定价，不能做"买 3Y PS 送 1Y ADP"的捆绑优化 |

---

### ISG B2B

#### ✅ Pros

| 优势 | 说明 |
|------|------|
| **极度简单** | 一个公式、一张表——任何人 5 分钟能理解 |
| **灵活应变** | 面对大客户压价、竞品突袭、特殊合同——人可以即时调整 PenRate |
| **谈判友好** | B2B 销售可以说"我帮你申请了一个特别 PenRate"，算法方案做不到这种"人情味" |
| **低系统门槛** | 不需要建模、不需要训练数据、不需要算法工程师——只需要一个有经验的定价经理和一张 Excel 表 |
| **适合复杂交易** | 捆绑、折扣、分层报价、跨 PN 打包——人可以在 PenRate 里把这些都"揉进去" |
| **快速启动** | 有历史 PenRate 数据就能跑，不需要等待模型训练和校准 |

#### ❌ Cons

| 劣势 | 说明 |
|------|------|
| **不可规模化** | 每新增一个 GEO/客群/PN 组合，需要人工判断 → 维护成本线性增长 |
| **不一致性风险** | 两个定价经理对同一场景可能定出不同的 PenRate——没有一致性约束 |
| **知识流失风险** | "为什么这个 PenRate 是 18%？"——答案在定价经理脑子里，离职即丢失 |
| **黑盒效应** | 从系统角度看，PenRate 就是一个数字——没有推导过程，无法审计"为什么是这个值" |
| **响应滞后** | HW 价格变化后，需要等人工判断 → 更新 PenRate 表 → 生效。市场竞争不等人 |
| **无自我优化** | 不会从成交/丢单数据中自动学习——每次都靠人重新判断 |
| **风控依赖人** | 如果定价经理没有充分理解 Margin 底线，PenRate 就可能定错 |

## 五、架构哲学对比

```
IDG E-com B2C（算法驱动）          ISG B2B（PenRate 驱动）
─────────────────────────          ─────────────────────
"把知识写进系统"                    "把知识留给专家"
"让算法做重复判断"                  "让人做综合判断"
"自动校准适应变化"                  "人工评估响应变化"
"一致性 > 灵活性"                  "灵活性 > 一致性"
"前期投入，后期省力"                "前期省力，后期费力"
```

## 六、相互借鉴的可能性

### ISG B2B 可以从 IDG E-com 学什么？

| 借鉴点 | 可行性 | 价值 |
|--------|:--:|------|
| PenRate **分维度拆解**（GEO × 客群 × Charge Type → 各自独立的 factor） | ✅ 高 | 把 PenRate 从一个黑盒数字变成 Band × Segment × Term 三个显式因子 |
| **季度自动校准**（PenRate 表按成交数据自动更新建议值） | ✅ 中 | 人可以覆盖，但系统给一个基准建议 |
| **下限/上限 Guardrail**（Floor/Cap 用 % of HW AUR 表达） | ✅ 高 | 防止 PenRate 漂移到不健康区间 |
| Attach Rate 闭环反馈 | ⚠️ 低 | B2B 交易量小、周期长，反馈信号太稀疏 |

### IDG E-com B2C 可以从 ISG B2B 学什么？

| 借鉴点 | 可行性 | 价值 |
|--------|:--:|------|
| **人工 Override 机制** | ✅ 高 | B2C 电商也可能需要大促折扣——保留人手动调价的能力 |
| **竞品对标模块**（PFV） | ✅ 中 | IDG 方案目前只做自身成本覆盖，引入 PFV 可增强市场竞争力 |
| **跨 PN 打包定价** | ⚠️ 低 | B2C 的场景不需要——消费者买一台电脑配一个服务，天然 1:1 |

## 七、结论

两个方案不是"谁更好"的问题，而是**场景适配**的问题：

- **IDG E-com B2C**：B2C 电商场景下，标准化 × 大流量 × 零人工接触 → 算法驱动是最优解
- **ISG B2B**：B2B 商机场景下，定制化 × 低流量 × 高接触谈判 → PenRate 驱动是务实选择

**但 ISG B2B 可以向前走一步**：把 PenRate 从一个黑盒数字拆成多个显式维度（Band × Segment × Term），逐项用数据驱动，逐步减少对人工判断的依赖——既不丧失 B2B 的灵活性，又获得算法的可扩展性。
