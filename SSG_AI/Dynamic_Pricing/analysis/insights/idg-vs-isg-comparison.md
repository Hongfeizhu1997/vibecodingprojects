# IDG vs ISG — Dynamic Pricing 方案对比

> 2026-07-10 | Dynamic Pricing 子项目 | 待决策
> 核心问题：Dynamic Pricing 引擎对 IDG（PC）和 ISG（服务器）应该统一方案还是分叉处理？

---

## 1. 背景

Dynamic Pricing 引擎同时覆盖 IDG（PC 产品线）和 ISG（服务器产品线）。两条产品线的业务特征差异显著——HW 型号数量、交易频率、单笔金额、数据可用性各不相同。核心待决策问题：

> **引擎层共享一套，但 PenRate 的确定方式应该统一（IDG 和 ISG 用同样方法），还是分叉（各用适合自己业务特征的方法）？**

---

## 2. 共同点 — 两条线可以共享什么

无论最终选择统一还是分叉，以下七项是两条线的最大公约数，可以共享：

| # | 共享要素 | 说明 |
|---|---------|------|
| 1 | **核心公式** | `ServicePrice = HWPrice × PenRate`，服务价格跟着硬件底盘走 |
| 2 | **六步引擎** | Intake → Comparable Benchmark → Candidate → Score → Guardrail → Output |
| 3 | **输出格式** | Price Band（Floor / Target / Stretch）+ Reason Code + Confidence Level |
| 4 | **四维输入** | HW Context / Service Economics / Deal Context / Historical Behavior |
| 5 | **约束体系** | Margin Floor → List Price Ceiling → DOA 三层 Guardrail |
| 6 | **设计原则** | 学习而非预设 · 独立于 HW 定价 · 渠道无关引擎 |
| 7 | **落地节奏** | 渐进信任：POC 离线验证 → Pilot 推荐参考 → Rollout 嵌入流程 |

> 结论：引擎框架可以统一。分歧在 **PenRate 确定方式** 这个环节。

---

## 3. 不同点 — 两条线的业务特征差异

| 维度 | ISG（服务器） | IDG（PC） |
|------|:---:|:---:|
| **HW 特征** | 型号少（数十款）、配置标准化、生命周期长 | 型号多（数百 SKU）、新季更新频繁、配置组合爆炸 |
| **交易特征** | 低频大单（$50K–$500K+） | 高频中小单（$500–$5K） |
| **历史数据量** | 少 — 同型号交易稀疏 | 多 — 可训练 Conversion Probability 模型 |
| **Comparable Benchmark 构建** | 同服务器型号 × Tier × GEO × 客户段 | 同 HW 价值段（PFV 区间）× Tier × GEO × 客户段 |
| **容错成本** | 高 — 单笔金额大，定价偏差影响显著 | 中低 — 单笔金额小，偏差被交易量分摊 |
| **可解释性需求** | 高 — 大单需向客户/审批方解释定价 | 中 — 可接受一定黑盒，辅助说明即可 |
| **新 SKU 频率** | 低 — 服务器型号更新周期长 | 高 — 每季新 PC 型号/配置上线 |

---

## 4. 两种路径的利弊

### 路径 A：统一方案

> ISG 和 IDG 使用相同的 PenRate 确定方式（都走 AI 计算，或都走规则查表）

**如果用 AI 统一（都走 IDG 模式）：**

| 优势 | 劣势 |
|------|------|
| ✅ 一套模型维护，降低长期维护成本 | ❌ ISG 数据量不足以训练有意义的模型 |
| ✅ 方法论一致，跨产品线沟通成本低 | ❌ ISG 冷启动 Confidence 低，实际退化为规则兜底 |
| ✅ 未来新增产品线可直接复用 | ❌ ISG 单笔金额大，模型偏差代价高 |
| ✅ 模型团队的技能复用 | ❌ ISG 低频交易使模型更新滞后 |

**如果用查表统一（都走 ISG 模式）：**

| 优势 | 劣势 |
|------|------|
| ✅ 上线快，不依赖历史数据 | ❌ IDG 数百 SKU × Tier × GEO 维度爆炸不可维护 |
| ✅ 完全可控可审计 | ❌ 放弃 IDG 海量交易数据的价值 |
| ✅ 审批友好 | ❌ IDG 无法响应 HW 涨/降价，损失利润或竞争力 |
| | ❌ IDG 每季新品需人工更新规则表 |

**统一方案的共同风险：迁就一端就会牺牲另一端——本质上是拿不同业务特征强行对齐。**

---

### 路径 B：分叉方案

> ISG 用固定查表（规则驱动），IDG 用 AI 计算（模型驱动）。引擎框架和输出格式共享，PenRate 确定方式各走各路。

| 优势 | 劣势 |
|------|------|
| ✅ 各取所长 — ISG 的"可控"和 IDG 的"规模效应"都不牺牲 | ❌ 两套维护体系，团队需要同时维护规则表和 ML 模型 |
| ✅ ISG 不因数据不足被迫上 AI，IDG 不因规则表限制数据价值 | ❌ 跨产品线方法论不统一，沟通和汇报需解释"为什么不同" |
| ✅ 共享引擎框架降低分叉成本 | ❌ 未来统一需要迁移成本 |
| ✅ 每条线可独立迭代，不互相拖慢 | ❌ 两条线之间无法共享学习（ISG 经验不能反哺 IDG 模型） |
