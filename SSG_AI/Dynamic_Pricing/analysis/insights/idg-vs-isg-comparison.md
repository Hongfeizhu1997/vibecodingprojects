# IDG vs ISG — Dynamic Pricing 方案对比

> 2026-07-10 | Dynamic Pricing 子项目
> 分析两条产品线的方案选择：为什么 ISG 用查表、IDG 用 AI，以及共享什么底座

---

## 1. 一句话结论

**两条路径不是竞争关系——是不同业务特征的必然选择。** ISG（低频高价值）数据不足以训练 AI，规则表是最优解；IDG（高频中低价值）数据足够，AI 带来额外收益。两条路径共享同一个引擎框架和 Price Band 输出格式。

---

## 2. 共同点（两方案共享同一引擎底座）

| # | 共享要素 | 说明 |
|---|---------|------|
| 1 | **核心公式** | `ServicePrice = HWPrice × PenRate`，服务价格始终跟着硬件底盘走 |
| 2 | **六步引擎** | Intake → Comparable Benchmark → Candidate → Score → Guardrail → Output，不分 IDG/ISG |
| 3 | **输出格式** | Price Band（Floor / Target / Stretch）+ Reason Code + Confidence Level |
| 4 | **四维输入** | HW Context / Service Economics / Deal Context / Historical Behavior |
| 5 | **约束体系** | Margin Floor（不亏）→ List Price Ceiling（合理）→ DOA（可控），三层 Guardrail |
| 6 | **设计原则** | 学习而非预设 · 独立于 HW 定价 · 同一引擎框架渠道无关 |
| 7 | **落地节奏** | 渐进信任：POC 离线验证 → Pilot 推荐参考 → Rollout 嵌入流程 |

---

## 3. 不同点

| 维度 | ISG（服务器） | IDG（PC） |
|------|:---:|:---:|
| **PenRate 来源** | 固定查表——多维矩阵手工定义 | AI 计算——模型从历史交易中学 |
| **模型类型** | 规则引擎（Rule-based） | ML 模型（Rule + ML 混合） |
| **HW 特征** | 型号少（SR650/SR850 等数十款）、配置标准化、生命周期长 | 型号多（ThinkPad 数百 SKU）、新季更新频繁、配置组合爆炸 |
| **交易特征** | 低频大单（单笔 $50K~$500K+） | 高频中小单（单笔 $500~$5K） |
| **历史数据量** | 少——同型号同配置的交易稀疏 | 多——可训练 Conversion Probability 模型 |
| **Comparable Benchmark 构建** | 同服务器型号 × Tier × GEO × 客户段 | 同 HW 价值段（PFV 区间）× Tier × GEO × 客户段 |
| **上线速度** | 快——2 周定义规则表即可 | 慢——需 2 个月数据清洗 + 特征工程 + 模型训练 |
| **可解释性** | 强——任何报价可追溯到具体规则格 | 中——Reason Code + Confidence 补偿，底层模型是黑盒 |
| **市场适应性** | 差——需人工更新规则表 | 好——模型自动吸收新交易模式 |
| **冷启动** | 容易——业务专家定义初始 PenRate | 困难——新市场/新 Tier 无历史数据时需借用相似市场先验 |
| **维护成本** | 维度膨胀后不可维护 | 模型需定期重训 + 监控漂移 |
| **核心竞争力** | 业务可控、审批友好 | 规模效应、持续优化 |

---

## 4. 优劣分析

### ISG 查表方案

**优势：**
- ✅ 上线极快：不依赖历史数据，业务拍定 PenRate 即可用
- ✅ 完全可控：PM 可直接调整任何格子的 PenRate
- ✅ 审批友好：规则表可审计，合规部门接受度高
- ✅ 适合低频高价值：ISG 单笔金额大（$50K+），错了代价高，保守方案更安全

**劣势：**
- ❌ 维度爆炸：3 个 Tier × 5 个 GEO × N 个型号 → 格数指数增长，跨型号/跨 GEO 的规则定义需 PM 逐格评审
- ❌ 不存在"最优"：PenRate 是"业务觉得合理"而非数据证明最优——高 PFV 服务器可能定价不足，低 PFV 可能竞争力不够
- ❌ 无法利用历史：已有的成交/丢单数据不反哺定价
- ❌ 无法响应市场变化：HW 涨价时 PenRate 不动 → 利润漏出；HW 降价时 PenRate 不动 → 服务价比竞品高
- ❌ 无法处理新场景：新服务器型号上线，PM 需凭经验拍 PenRate——和当前做法没区别

### IDG AI 方案

**优势：**
- ✅ 自动适应：HW 涨价 → 引擎评估上调 PenRate 是否损害成交概率；HW 降价 → 引擎上调 PenRate 守住服务收入
- ✅ 捕捉非线性：同一个 $1,500 价位，ThinkPad X1 和 ThinkBook 的企业客户支付意愿不同——AI 可以学到这个差异，规则表做不到
- ✅ 持续学习：每笔成交/丢单都在优化模型，PenRate 推荐越来越准
- ✅ 规模效应：IDG PC 交易量大（每天数百笔），AI 方案的优势随数据量增长
- ✅ 可复制：B2B 引擎训练好后，Consumer/SMB 只需换输入权重，不换引擎

**劣势：**
- ❌ 冷启动困难：新市场/新 Tier 无历史数据时 Confidence 低，实际退化为规则兜底
- ❌ 需要训练数据：至少需要几千条历史成交记录才能训练有意义的 Conversion Probability 模型
- ❌ 可解释性弱：销售问"为什么推荐 12% 不是 10%"，模型可以给 Reason Code 但不能像规则表那样"因为你查的是第 3 行第 5 列"
- ❌ 模型维护成本：需监控数据漂移、定期重训、A/B 验证
- ❌ 上线周期长：POC 2 个月 + Pilot 3 个月才能 Rollout

---

## 5. 落地建议

**不建议试图用一套方法统一两条线。** 各取所长：

```
ISG：投入聚焦规则表的维护工具化 — 降低 PM 手工维护成本
IDG：投入聚焦模型精度和采纳率 — POC → Pilot → Rollout 按 V3 路线图推进
```

两条路径共享同一个引擎框架和 Price Band 输出格式，未来可横向整合。但当前阶段的核心差异（数据量级、交易频率、容错成本）决定了方法论必须分叉。
