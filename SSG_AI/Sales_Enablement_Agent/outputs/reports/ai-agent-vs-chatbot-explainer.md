# SSG Sales Enablement Agent —— 为什么需要在 Spark 之外再做一层

> **面向**：SSG GPS 业务团队  
> **目的**：解释在已有 Spark（Chatbot）和 Codex 自建 Agent 的基础上，为什么还需要一个企业级 AI Agent 平台  
> **日期**：2026-07-01

---

## 1. Spark 帮了很多忙——但它天生只能走到这里

### 1.1 Spark 今天在做什么

Spark 作为一个 Chatbot，处理的是"你问它答"类问题：

> **你**："PN 创建流程是什么？"  
> **Spark**：返回知识库里的流程说明。

这类 FAQ 场景 Spark 做得不错——它让团队不用翻文档就能快速查到规则和流程。

### 1.2 但团队每天还在手工做的事，Spark 做不了

这不是 Spark 不够好。是 **Chatbot 这个品类的能力边界就到这里**——它能"答"，不能"做"。

团队每天仍在手动处理的：

| 操作 | 当前做法 | 为什么 Spark 帮不上 |
|------|---------|-------------------|
| ODT 属性变更影响分析 | 人工跨 ODT → Concord → CPM 手动查询拼凑，耗时数小时 | Spark 不能调系统 API，不能查实时数据 |
| MT 公告巡检 | 人工刷 ICP，经常漏 | Spark 不会主动抓取、不会推送 |
| PN 主数据查询 | 写 SQL 或找人拉报表 | Spark 连不上 CPM/Concord，不知道你的 PN 实时状态 |
| Booking 影响面评估 | 人工对多个 Excel | Spark 不懂 Booking 数据结构，不会做聚合分析 |

**一句话**：Spark 是"会说话的百科"。这些场景需要一个"会干活的助手"。

### 1.3 Codex 搭的 Agent 呢？——它们是工具，不是平台

IT 同事用 Codex / Claude Code 等工具确实可以加速单个场景的开发。但它们解决的是"写代码更快"的问题，不是"建成后全团队可持续使用"的问题。

用 Codex 搭 Agent 的典型模式：

```
场景 #1（ODT 查询）→ 写一套代码 → 能用
场景 #4（MT 捕获） → 再写一套代码 → 也能用
场景 #12（PN 查询）→ 又写一套代码 → 也能用
...
```

**问题不在能不能搭出来——在搭出来之后**：
- 每加一个场景，系统集成、安全控制、角色权限都要重新写一遍
- 三个场景三套代码，规则变了要改三个地方
- 只有开发它的 IT 同事能维护——业务团队改不了
- 场景之间不共享知识——MT 捕获的知识，ODT 分析用不上

### 1.4 还有你们自己用 vibe coding 做的小工具——这是最强的信号

很多同事已经在用 vibe coding（自然语言描述需求，AI 直接生成小工具）自己动手解决重复性操作了。**这恰恰证明了自动化需求的真实性和紧迫性**——业务人员不等 IT 排期，自己上手，说明痛点足够痛。

但这些小工具有天然的天花板：

| vibe coding 小工具的长处 | vibe coding 小工具的局限 |
|------------------------|------------------------|
| ✅ 快——描述需求几分钟出原型 | ❌ **单人单用**：你写的脚本同事用不了，或者用起来提心吊胆 |
| ✅ 灵活——想改什么直接说 | ❌ **无安全边界**：Booking 数据可能被直接发给外部 AI，没有脱敏 |
| ✅ 不用等排期——自己就能动手 | ❌ **无人维护**：你写的脚本只有你能改，人走了工具就废了 |
| | ❌ **无法跨系统**：一个脚本通常只调一个系统，做不到"查 ODT → 调 Concord → 交叉分析" |
| | ❌ **知识不沉淀**：每个人的小工具是自己的，团队积累不下来 |

**vibe coding 小工具 + Spark + Codex Agent——这三种方式本质上都是"点状方案"**。它们证明了需求真实存在，但各自都有碰不到的天花板。

## 2. 四种方案的能力边界：Spark / Vibe Coding / Codex Agent / 企业 Agent 平台

| 能力维度 | Spark（Chatbot） | Vibe Coding 小工具 | Codex 自建 Agent | **SSG Enablement Agent** |
|---------|:--:|:--:|:--:|:--:|
| 知识问答 | ✅ 做得很好 | ❌ | ✅ | ✅ |
| 跨系统实时数据查询 | ❌ 品类天花板 | ❌ 通常只连一个系统 | ⚠️ 能，但每系统单独开发 | ✅ 内置 6 系统 API 连接 |
| 多步任务自动串联 | ❌ | ❌ | ⚠️ 能，但每场景手写编排 | ✅ 协调员自动拆解→分派→汇总 |
| 审批控制（自动/需批） | ❌ | ❌ | ❌ 需从零搭建 | ✅ 内置两级安全机制 |
| 敏感数据脱敏 | ❌ | ❌ 数据可能直发外部 AI | ❌ 需从零搭建 | ✅ Booking 数据自动掩码 |
| 操作审计追溯 | ❌ | ❌ | ❌ 需从零搭建 | ✅ 全链路日志 |
| 多角色差异化 | ❌ | ❌ | ❌ 需从零搭建 | ✅ PM / Pricing / Finance 各自专属 |
| 主动监控推送 | ❌ | ❌ | ⚠️ 需单独写定时任务 | ✅ MT 公告自动捕获 + 推送 |
| 团队记忆 | ❌ | ❌ | ❌ | ✅ 跨会话记住偏好和操作 |
| 知识复利 | ❌ | ❌ 知识困在个人脚本里 | ❌ 场景间不共享 | ✅ 每个场景自动丰富共享知识库 |
| 团队共享 | ❌ | ❌ 单人单用 | ⚠️ 可以但不安全 | ✅ 设计即多用户 |
| 业务团队可维护 | ❌ | ⚠️ 能写不能修 | ❌ 依赖 IT | ✅ 知识库更新即全局生效 |
| 部署 | SaaS | 外部 AI 服务 | 看怎么搭 | 联想内部部署 |

**四种方式的共同点**：Spark、vibe coding、Codex Agent 都证明了自动化需求真实存在。**区别在于**：前三者是点状方案，每解决一个问题都要从头搭一套；我们的方案是平台——基础设施建一次，场景越加越快。

## 3. 我们的方案：一个会干活的 AI 团队

### 3.1 一句话概览

你有一个 AI 团队——一个**协调员** + 四个**专员** + 一套**共享知识库**——全部在 Teams 里可用。

```
你（Teams）
    ↓
┌──────────────────────────────────┐
│  协调员（Master Agent）           │  ← 理解你的意图，分派给对应专员
│  你问"PN X 的 sales cost？"      │
│  → 它判断：这是成本问题，找成本专员│
└──────────┬───────────────────────┘
           │
    ┌──────┼──────┬──────────┐
    ▼      ▼      ▼          ▼
┌──────┐┌──────┐┌──────┐┌──────┐
│PN    ││成本  ││定价  ││生命  │    ← 四个专员，各司其职
│专员  ││专员  ││专员  ││周期  │
│      ││      ││      ││专员  │
└──┬───┘└──┬───┘└──┬───┘└──┬───┘
   │       │       │       │
   └───────┴───────┴───────┘
           │
    ┌──────┴──────────────────────┐
    │  共享知识库                  │  ← SOP、规则、定义，所有专员共用
    │  PN 流程 · Tier 规则 · 审批   │
    │  矩阵 · ODT 定义 · 风险映射   │
    └─────────────────────────────┘
```

**业务类比**：就像客服团队有 billing、returns、technical support 三个专员，各管一摊，背后共享一套 SOP。你不需要知道该找谁——协调员自动帮你路由。

### 3.2 四个专员覆盖的职责

| 专员 | 覆盖场景 | 示例 |
|------|---------|------|
| **PN 专员** | PN 数据查询、ODT 变更影响分析 | "PN-XXXXX 的 Booking 影响面？" |
| **成本专员** | Sales Cost 计算、Uplift 规则 | "这批 PN 的标准成本是多少？" |
| **定价专员** | PFV 竞品对标、List/Channel Price | "竞品在这个 Tier 的价格区间？" |
| **生命周期专员** | PN 关闭筛选、MT 公告捕获 | "哪些 PN 可以关闭了？" |

> **关键设计**：四个专员共享一套知识库——PN 流程规则、审批矩阵、Tier 定义——不需要通过另一个"知识专员"中转。就像任何专员都能直接翻 SOP 手册，不需要找专人查。

### 3.3 覆盖场景

| # | 场景 | Wave |
|---|------|------|
| 1 | ODT 属性变更影响分析 + Booking Impact | Wave 1 |
| 4 | MT & Service Tier Announcement 自动捕获 | Wave 1 |
| 12 | PN 主数据查询（客制化报告） | Wave 1 |
| 2 | PN 需求自动生成 POR Excel | Wave 2 |
| 3 | 新 PN 重复检查 | Wave 2 |
| 5 | PN 生命周期管理（筛选+审批） | Wave 2 |
| 7 | PN 创建/扩展判断 + 默认值填充 | Wave 2 |
| 6 | Sub-Tier 定义 | Wave 3 |
| 8 | 标准成本计算 | Wave 3 |
| 9 | Sales Cost Uplift 规则定义 | Wave 3 |
| 10 | PFV 竞品价格监控 | Wave 3 |
| 11 | List/Channel Price 计算 | Wave 3 |
| 13 | 新人 Onboarding | Wave 4 |

### 3.4 安全设计

| 级别 | 示例 | 说明 |
|------|------|------|
| 🟢 **自动执行** | 查询 PN 数据、生成报告、MT 公告入库 | AI 直接完成，结果给你看 |
| 🔴 **需你审批** | 成本写入 CPM、价格发布、PN 批量关闭 | AI 出建议→你看过点确认→AI 执行 |

**数据安全**：Booking 数据中的客户名称在进 AI 分析前自动脱敏。全链路操作可追溯。

### 3.5 与 Spark 的关系：互补，不替代

- **Spark 继续做它擅长的事**：FAQ 问答、流程指引——团队已经用熟了，不需要改
- **Agent 覆盖 Spark 做不了的事**：跨系统数据查询、多步分析、主动监控推送
- 两者在同一个 Teams 里共存——用户不需要区分"该找谁"，自然语言提问即可

## 4. 经济账：为什么平台比点状方案更划算

### 4.1 场景增加的边际成本

用 Codex 自建 Agent 的模式：每加一个场景，系统集成、安全控制、权限管理都要重新开发。**第 1 个场景和第 13 个场景的投入差不多。** Vibe coding 小工具更极端——每个工具是独立脚本，十个工具之间零共享、零复用。

企业 Agent 平台的模式：基础设施（系统连接、审批机制、安全层、知识库）只建一次。**场景越多，边际成本越低。**

```
Codex 自建 Agent：每个场景独立开发
  场景 #1  ■■■■  4 周
  场景 #2  ■■■■  4 周
  场景 #3  ■■■■  4 周
  ...
  场景 #13 ■■■■  4 周
  总计：52 周开发 + 13 套独立维护

SSG Enablement Agent：基础设施一次建设，场景叠加复用
  平台基础  ■■■■■■  6 周（系统连接 + 安全 + 知识库 + 审批）
  场景 #1   ■■     2 周
  场景 #2   ■■     2 周
  场景 #3   ■      1 周
  ...
  场景 #10+ ■      2-3 天
  总计：~20 周覆盖全部 13 场景 + 1 套统一维护
```

**13 个场景全部覆盖后，总投入约为 Codex 自建的 40%，且只维护一套系统。**

### 4.2 知识复利：每个场景让下一个场景更聪明

这是点状方案做不到的事情：

- 场景 #1（ODT 变更分析）上线 → 共享知识库积累了"变更类型 → 风险等级"的映射规则
- 场景 #5（PN 生命周期管理）上线 → **自动继承**上面的风险映射，不需要重新定义
- 场景 #13（新人 Onboarding）上线 → **自动拥有**前面 12 个场景积累的全部 PN 流程知识

**Codex 自建 Agent 做不到这一点**——每个 Agent 的知识是孤立的。A Agent 分析过的风险规则，B Agent 完全不知道。

### 4.3 维护成本：改一处 vs 改 N 处

| 维护场景 | Codex 自建 Agent | SSG Enablement Agent |
|---------|-----------------|---------------------|
| PN 审批规则变了 | 找到涉及的所有 Agent，逐一改代码 | 更新知识库一条规则，所有专员即时生效 |
| 新增一个业务系统 | 每个 Agent 单独对接新系统 API | 对接一次，所有专员可用 |
| 新增一个用户角色 | 每个 Agent 各自加权限逻辑 | 配置一次角色定义，全局生效 |
| IT 同事离职 | 接手的人要读懂 N 套独立代码 | 接手的人维护一个平台 |

## 5. 不投的隐性成本

维持现状，团队继续用 Spark + Codex 自建 Agent 的模式，会面临：

| 风险 | 具体表现 |
|------|---------|
| **MT 公告漏盯** | 一天几十条公告靠人工巡检，漏一条可能导致合规问题或 PN 创建延误 |
| **ODT 变更响应慢** | 一个属性变更手工跨 3-4 个系统评估影响面，数小时才能出结论——期间可能已有新 Booking 按旧属性下单 |
| **知识依赖个人** | 老员工知道该查哪个系统、看哪个字段——人走了经验就没了。没有系统化沉淀 |
| **场景越多越吃力** | 每加一个新场景，IT 同事要重新搭一套——开发排期越来越长 |
| **安全边界模糊** | 自建 Agent 没有统一的审批机制，谁调了什么、改了什么——难以追溯 |
| **vibe coding 数据泄露风险** | 业务同事用小工具处理 Booking 数据时，可能无意中将客户信息发给外部 AI——没有脱敏、没有审计、合规盲区 |

## 6. 总结与建议

### Spark + Agent = 完整的 AI 能力覆盖

```
          Spark              │      SSG Enablement Agent
─────────────────────────────┼─────────────────────────────
  你问"流程是什么"             │  你问"这个 PN 的 Booking 影响面"
  → Spark 答知识库内容         │  → Agent 自动跨 ODT/Concord/CPM 查询分析
                              │
  FAQ、流程指引                 │  实时数据查询、多步分析、主动监控
  继续用，不需要改               │  新能力，覆盖 Spark 做不了的
```

### 建议：Wave 1 先跑通，用结果说话

**Wave 1（4-6 周，3 个场景，全部只读）**：

| 场景 | 做什么 | 为什么先做 |
|------|--------|----------|
| #12 PN 主数据查询 | 自然语言查 PN 信息，替代写 SQL | 最常用，即时见效 |
| #1 ODT 变更影响分析 | 自动跨系统查 Booking 影响面 | 最高价值，省时最多 |
| #4 MT 公告自动捕获 | 定时抓取 ICP 公告，主动推送 | 堵住漏盯风险 |

**全部只读操作，零系统破坏风险。** 跑通后让团队实际使用 2-4 周，收集反馈，再决定是否继续 Wave 2。
