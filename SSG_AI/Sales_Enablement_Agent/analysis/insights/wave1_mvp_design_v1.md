# Wave 1 MVP 详细设计 — Knowledge Pipeline + Teams Bot

> 创建：2026-06-17 | 更新：2026-06-18 | 版本：v1.1 | 子项目：Sales Enablement Agent
> 基于：架构方案 V1 (§8 落地路径) + 平台评估 + iChain 适配清单

## 1. Wave 1 定位

### 一句话

用最小的技术风险和最短的上线周期，验证「AI 辅助 SSG GPS 团队做数据查询和影响分析」的实际价值。

### 为什么从知识查询开始

| 理由 | 说明 |
|------|------|
| **只读操作** | 3 个场景全部是数据查询/分析，不涉及系统写入——零破坏性风险 |
| **即时价值** | ODT 变更分析、MT 公告捕获、PN 主数据查询是团队每天在做的重复操作 |
| **验证可行性** | 验证系统 API 可用性、知识库质量、Teams Bot 交互体验 |
| **建立信任** | 让业务团队先用起来，看到 AI 辅助的实用性，为 Wave 2 操作自动化铺路 |

### 包含 / 不包含

| 包含（Wave 1） | 不包含（Wave 2-4） |
|---------------|-------------------|
| #1 ODT 属性变更影响分析 + Booking Impact | #2 PN 需求自动生成 POR |
| #4 MT & Service Tier Announcement 捕获 | #3 PN 重复检查 |
| #12 PN 主数据查询（客制化报告） | #5 PN 生命周期管理 |
| Teams Bot 对话交互 | Web Persona Workspace |
| RAG 知识库（PN 流程/规则/审批） | 系统写入操作 |
| 审批通知（只发通知，不执行操作） | Cost/Price 计算 |

## 2. 场景 #1：ODT 属性变更影响分析 + Booking Impact

### 2.1 场景描述

ODT（Offering Data Tool）管理服务 PN 的属性变更（如 Warranty Term 调整、Service Tier 升降、Region 扩展）。当属性变更发生时，团队需要快速评估：
- 影响了哪些 Booking？（已下单未交付的订单）
- Booking Impact 的金额范围？
- 变更的风险等级？

当前做法：人工在多个系统间手动查询拼凑。

### 2.2 端到端流程

```
┌─────────────────────────────────────────────────────────────┐
│  用户触发                                                      │
│  Teams: "@Agent ODT 变更 PN-XXXXX Warranty Term 1Y→3Y，      │
│          帮我看看影响面"                                        │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: Master Agent 意图识别                                │
│  • 识别：RAG Pipeline · ODT 变更分析                       │
│  • 提取：PN=XXXXX, 变更类型=Warranty Term, 1Y→3Y             │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: ODT API 查询（自动执行）                              │
│  • 调 ODT API：获取 PN-XXXXX 当前属性、历史变更记录            │
│  • 返回：Service Tier, Warranty, Region, Pricing 等属性       │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: Booking 关联查询（自动执行）                           │
│  • 调 Booking 系统（Concord/内部 DB）：                        │
│    筛选含 PN-XXXXX 且 Status=Open/In-Process 的 Booking       │
│  • 返回：Booking ID, Customer, Qty, Amount, Status, Geo      │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 4: AI 影响分析 & 风险评级（自动执行）                     │
│  • 变更类型 → 影响维度映射：                                   │
│    Warranty Term ↑ → 成本 ↑, 定价需重算                       │
│    Service Tier ↓ → 利润影响, Geo 合同约束                     │
│    Region 扩展 → 新市场合规检查                                │
│  • Booking 金额聚合 → 影响范围估算                             │
│  • 风险评级：Low / Medium / High（规则引擎）                    │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 5: 生成分析报告 → 返回用户                                │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ ODT 变更分析：PN-XXXXX                                │    │
│  │ 变更：Warranty Term 1Y → 3Y                          │    │
│  │ 风险：⚠️ Medium                                       │    │
│  │                                                      │    │
│  │ Booking Impact：                                      │    │
│  │ • 受影响 Booking：12 笔                               │    │
│  │ • 总金额：$4.2M（按当前 List Price 估算）              │    │
│  │ • Top 3 影响客户：                                    │    │
│  │   Customer A | Booking #B001 | $1.2M                │    │
│  │   Customer B | Booking #B003 | $850K                │    │
│  │   Customer C | Booking #B007 | $620K                │    │
│  │                                                      │    │
│  │ 建议动作：                                            │    │
│  │ • 通知 Pricing Team 重算 List Price                  │    │
│  │ • 通知 Finance 评估成本影响                           │    │
│  │ • 通知受影响的 Geo Sales Enablement                   │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

## 3. 场景 #4：MT & Service Tier Announcement 捕获

### 3.1 场景描述

MT（Machine Type）发布时会公告关键信息：target price、announce date、service tier 归属等。团队需要从多个渠道（邮件、ICP、内部公告）手动收集 MT 公告并提取关键字段入库。

AI 要做：自动监听 MT Announcement → 提取结构化字段 → 入库 → 推送给相关人员。

### 3.2 端到端流程

```
┌─────────────────────────────────────────────────────────────┐
│  Trigger 1: 定时轮询（每 N 小时）                              │
│  • 监听 ICP 新增 MT Announcement                              │
│  • 监听邮件（指定邮箱/关键词）                                  │
│                                                               │
│  Trigger 2: 手动触发                                          │
│  • Teams: "@Agent 检查最近 7 天的新 MT Announcement"          │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 获取原始公告                                         │
│  • ICP API：查询 New Announcement（含 target price, date）     │
│  • 邮件解析：NLP 提取 MT 型号、公告字段                        │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 结构化提取（LLM 处理）                                │
│  • 输入：原始公告文本/JSON                                    │
│  • 输出结构化字段：                                            │
│    MT Model | Announce Date | Target Price | Service Tier   │
│    Sub-Tier | Warranty Term | Geo Region | Source           │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 去重 & 入库                                          │
│  • 与已有记录去重（MT Model + Announce Date 联合唯一键）       │
│  • 写入 MT Announcement 数据库表                              │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 4: 推送通知（自动）                                      │
│  • Teams 通知 → 相关 Persona（GPS PM, Pricing Team）          │
│  • 摘要卡片：MT Model, Target Price, Service Tier             │
│  • 通知内容示例：                                              │
│    ┌─────────────────────────────────────────────────┐      │
│    │ 🔔 新 MT Announcement                            │      │
│    │ ThinkPad X1 Carbon Gen 13                        │      │
│    │ Target Price: ¥12,800 | Service Tier: Premium    │      │
│    │ Announce Date: 2026-06-20 | Region: Global        │      │
│    │ [查看详情]  [忽略]                                │      │
│    └─────────────────────────────────────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 定时任务设计

| 参数 | 值 |
|------|-----|
| 轮询频率 | 每 4 小时（工作日） |
| 监听源 | ICP API、指定邮箱 |
| 去重策略 | MT Model + Announce Date 联合唯一键 |
| 推送对象 | GPS PM 频道、Pricing Team 频道 |
| 数据保留 | 6 个月历史 |

### 3.4 数据依赖

| 数据 | 来源 | 获取方式 | 状态 |
|------|------|---------|------|
| MT Announcement | ICP | API / 数据推送 | [待确认 API] |
| 邮件监听 | Outlook/Exchange | Graph API / IMAP | [待确认邮箱权限] |
| 已有 MT 记录（去重用） | 本地 DB | SQLite / PostgreSQL | MVP 阶段可轻量 |

## 4. 场景 #12：PN 主数据查询

### 4.1 场景描述

团队日常高频操作：查 PN 的属性、Sales Cost、Booking 关联、生命周期状态。目前需要在 ICP/SPEP/SCFE/CPM 多个系统间切换。

AI 要做：自然语言单次提问 → 跨系统聚合 → 一张卡片返回。

### 4.2 支持的查询类型

| 查询类型 | 示例问法 | 涉及系统 |
|---------|---------|---------|
| PN 属性 | "PN-XXXXX 的 Service Tier 和 Warranty 是什么？" | ICP, ODT |
| Sales Cost | "PN-XXXXX 的最新 Sales Cost 是多少？" | CPM |
| Booking 关联 | "PN-XXXXX 有哪些未关闭的 Booking？" | Concord |
| 生命周期 | "PN-XXXXX 是否在关闭候选名单里？" | SPEP + 业务规则 |
| 组合查询 | "亚太区 Premium Tier 里 Sales Cost 低于 $500 的 PN 有哪些？" | 多系统 JOIN |
| 报告查询 | "Top 10 Booking 客户，按 PN 分类" | Booking + PN 关联 |

### 4.3 端到端流程

```
┌─────────────────────────────────────────────────────────────┐
│  用户: "@Agent PN-XXXXX 的 Sales Cost 和 Booking 情况"        │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 1: 意图解析 → Query Plan                                │
│  Master Agent 拆解为子查询：                                   │
│  Plan: [①查 CPM 取 Sales Cost] → [②查 Concord 取 Booking]    │
│  两个子查询可并行                                              │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 2: 并行执行子查询（自动）                                │
│  ① CPM API → { Sales Cost: $1,250, Effective Date: 2026-...}│
│  ② Concord API → { Booking Count: 45, Total Amt: $18.3M }   │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────────┐
│  Step 3: 聚合 & 格式化                                       │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ 📋 PN-XXXXX                                          │    │
│  │ Service Tier: Premium | Warranty: 3Y On-site         │    │
│  │                                                      │    │
│  │ 💰 Sales Cost                                        │    │
│  │ Current: $1,250 | Effective: 2026-Q2                  │    │
│  │ Previous: $1,180 | Change: +5.9%                      │    │
│  │                                                      │    │
│  │ 📦 Booking Summary                                   │    │
│  │ Active: 45 bookings | Total Amount: $18.3M           │    │
│  │ Top Customer: Customer A (12 bookings, $5.2M)        │    │
│  │                                                      │    │
│  │ 🔗 [在 SPEP 中查看] [在 CPM 中查看]                    │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### 4.4 查询能力矩阵

| 复杂度 | 示例 | 涉及系统数 | 响应时间目标 |
|--------|------|-----------|-------------|
| 简单查询 | "PN-XXXXX 的 Sales Cost" | 1 个系统 | < 3s |
| 跨系统查询 | "PN-XXXXX 的 Cost + Booking" | 2-3 个系统 | < 8s |
| 聚合查询 | "亚太区 Premium Tier PN 列表" | 多系统 JOIN | < 15s |
| 报告查询 | "Top 10 Booking by PN" | 多系统聚合 | < 30s |

## 5. Teams Bot 交互设计

### 5.1 交互模式

```
模式 1: @提及 主动问答
┌────────────────────────────────────────┐
│ User: @Agent PN-XXXXX 的 Sales Cost？  │
│ Agent: [查询中...]                     │
│ Agent: 📋 PN-XXXXX Sales Cost: $1,250  │
└────────────────────────────────────────┘

模式 2: 通知推送（到频道/个人）
┌────────────────────────────────────────┐
│ Agent → #gps-pm-channel                │
│ 🔔 新 MT Announcement: ThinkPad X1...  │
│ [查看详情]                              │
└────────────────────────────────────────┘

模式 3: 审批通知（只通知，不执行操作）
┌────────────────────────────────────────┐
│ Agent → @User (DM)                     │
│ ⚠️ ODT 变更分析完成                      │
│ PN-XXXXX | Risk: Medium | Impact: $4.2M│
│ [查看完整报告]  [转发审批]               │
└────────────────────────────────────────┘
```

### 5.2 命令设计

所有命令通过自然语言触发，不设计 `/command` 前缀。Master Agent 做意图识别。

| 意图 | 触发示例 | 映射场景 |
|------|---------|---------|
| ODT 影响分析 | "ODT 变更 PN-XXXXX" / "分析 PN-XXXXX 的影响面" | #1 |
| Booking 影响 | "PN-XXXXX Booking 受影响吗" / "Booking Impact" | #1 |
| MT 公告 | "最近 MT 公告" / "新 MT Announcement" / "检查 MT" | #4 |
| PN 查询 | "PN-XXXXX" / "查 PN-XXXXX 的..." | #12 |
| 组合查询 | "亚太区 Premium PN 的 Sales Cost" | #12 |
| 帮助 | "你能做什么" / "help" | 通用 |

### 5.3 对话状态管理

```
┌──────────┐    意图识别     ┌──────────────┐
│  空闲     │ ───────────→  │ 查询执行中    │
│ (idle)   │                │ (processing) │
└──────────┘                └──────┬───────┘
     ▲                             │
     │         结果返回             │
     └─────────────────────────────┘

如果用户在同一查询执行期间发送新消息：
→ 如果新消息与当前查询相关（追加条件）：合并上下文
→ 如果新消息是全新查询：取消当前查询，开始新查询
```

### 5.4 错误处理 & 降级

| 情况 | 响应 |
|------|------|
| 系统 API 不可用 | "抱歉，CPM 系统当前不可用。请稍后重试或[在 CPM 中手动查看]" |
| 查询超时 | "查询超过 15 秒，已返回部分结果。完整报告将在后台生成后通知你。" |
| 无结果 | "未找到 PN-XXXXX 的相关数据。请确认 PN 编号是否正确。" |
| 权限不足 | "你当前没有访问该 Booking 数据的权限。请联系 [Geo Lead] 申请权限。" |
| 模糊查询 | "你想查 PN-XXXXX 的哪个信息？Sales Cost / Booking / 属性？" |

### 6.1 简化全栈

```

├───────────────────────────────────────────┤
│       SHARED KNOWLEDGE PIPELINE (RAG)      │
│  ┌──────────┬──────────┬──────────┐        │
│  │ #1 ODT   │ #4 MT    │ #12 PN    │        │
│  │ Analyzer │ Monitor  │ Query     │        │

│       │          │          │              │
├───────┴──────────┴──────────┴──────────────┤
│          INTEGRATION (MCP/Toolcall)         │
│   ICP  │  ODT  │  Concord  │  CPM  │ SPEP  │
│  (MT)  │(Attr) │ (Booking) │(Cost) │(PN)   │
├───────────────────────────────────────────┤
│       RAG KNOWLEDGE BASE (内容层)           │

│  DeerFlow (Vetraflow) + Lenovo Hybrid AI   │
└───────────────────────────────────────────┘
```

### 6.2 Wave 1 与完整架构的差异

| 层级 | 完整架构（V1） | Wave 1 MVP | 原因 |
|------|--------------|-----------|------|
| Channel | Teams + Web + Embedded | Teams Only | 最快上线渠道 |
| Persona Workspace | 4 个 Workspace | 无独立 Workspace | 先用 Teams 对话代替 |
| Sub-Agent | 4 个 (PN/Cost/Price/Lifecycle) | 0 个操作类 | W1 只做查询，RAG 直连 Master |
| RAG Pipeline | 共享管线（所有 Sub-Agent 调用） | 直连 Master Agent（面用户） | 无操作 Agent 时 RAG 承担交互角色 |
| Safety Layer | Auto + Approval 两级 | Auto Only | 无需审批（只读） |
| Integration | 6 个系统 | 5 个系统（无 SCFE） | #8 成本计算不在 W1 |

### 6.3 RAG 知识库清单

| 知识域 | 内容 | 来源 | 优先级 |
|--------|------|------|--------|
| PN 生命周期规则 | Create/Extend/End-of-Life 判断条件 | 内部 SOP 文档 | P0 |
| Service Tier 体系 | Tier 定义、归属规则 | 业务文档 | P0 |
| 审批规则 | 哪些操作需要哪级审批 | 审批矩阵 | P1 |
| ODT 属性字段定义 | 每个属性的含义、影响维度 | ODT 文档 | P0 |
| MT Announcement 字段 | 公告包含哪些字段、格式 | ICP 文档 | P0 |
| 风险映射表 | 变更类型 → 风险等级 | 业务经验沉淀 | P1 |
| Booking 数据脱敏规则 | 哪些字段不能直接展示 | 安全合规文档 | P0 |

## 7. 成功指标 (KPIs)

| 指标 | 目标 | 测量方式 |
|------|------|---------|
| **采纳率** | ≥ 30% 目标用户每周至少使用 1 次 | Teams Bot 活跃用户统计 |
| **查询成功率** | ≥ 85% 查询在目标时间内返回有效结果 | Agent 日志分析 |
| **MT 公告捕获率** | ≥ 95% ICP 公告被自动捕获 | 人工抽查 vs Agent 捕获量 |
| **NPS / 满意度** | ≥ 7/10（MVP 后用户调研） | Teams 内嵌评分按钮 |
| **时间节省** | 平均每次查询节省 3-5 分钟（vs 手动跨系统查询） | A/B 对比 + 用户自报 |
| **数据覆盖率** | 至少 60% PN 可通过 Agent 查询到完整属性 | 查询成功率按 PN 维度统计 |

### 不做 KPI（避免过早优化）

- ❌ 不追求响应时间 < 2s（不确定系统 API 延迟）
- ❌ 不追求 100% 查询覆盖（有些 PN 可能历史数据不完整）
- ❌ 不追求自然语言理解 100% 准确（允许澄清追问）

## 8. 风险 & 假设

### 8.1 关键假设（需在 MVP 前验证）

| # | 假设 | 验证方式 | 风险 |
|---|------|---------|------|
| H1 | ICP/ODT/CPM/Concord 提供可调用的 API | 与 IT 团队确认 | **高** — 如无 API 则无法自动查询 |
| H2 | Teams Bot 可通过 DeerFlow IM Gateway 接入 | 参考 DeerFlow 文档 + IT 评估 | **中** — 可能需要额外审批 |
| H3 | PN 流程/规则有成文文档可供 RAG 摄入 | 收集现有 SOP/文档 | **中** — 如果只有口头知识，RAG 效果受限 |
| H4 | Lenovo Hybrid AI Platform 已就绪可部署 | 与 AI 平台团队确认 | **中** |
| H5 | Booking 数据可脱敏后在 LLM 上下文中使用 | 与安全团队确认数据策略 | **高** — SaaS LLM 安全问题 |

### 8.2 已知风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 系统 API 延迟高 | 查询超时，体验差 | 前端展示「查询中」状态 + 超时降级 |
| SaaS LLM 数据安全 | 合规风险 | 最小化数据传递 + 脱敏 + 私有化部署评估 |
| 自然语言理解不准 | 错误查询 | 容忍澄清追问 + 关键字段回显确认 |
| 知识库质量低 | RAG 效果差 | 先手动整理核心规则，逐步扩充 |

| 交付物 | 说明 | 产出形式 |

### 建议里程碑

```
Week 1-2: 假设验证
├── 确认系统 API 可用性（H1）      ← 🚨 阻塞项
├── 确认 Teams Bot 接入方案（H2）
├── 收集知识库原材料（H3）
└── 确认数据安全策略（H5）

Week 3-4: 核心开发
├── RAG 知识库搭建（P0 项）
├── 3 个场景的 Skill 定义
├── ICP/ODT/Concord/CPM MCP Tools
└── Master Agent 意图识别 Prompt

Week 5-6: 集成测试 & 内测
├── Teams Bot 部署到测试频道
├── 内测用户（GPS PM × 2 + Pricing × 1）
├── 收集反馈 → 迭代
└── 准备生产环境

Week 7-8: 上线 & 监测
├── 生产 Teams 频道上线
├── KPI 埋点（采纳率、成功率、满意度）
├── 2 周后复盘
└── 决定是否进入 Wave 2
```
