## 1. 为什么先谈产品推荐

产品推荐（服务智能推荐）是 SSG 服务变现的"临门一脚"——客户买了硬件，服务能不能 attach 出去，就在推荐这一步。

选它作为第一块示范切片，有三个理由：

1. **它是已跑通的域**：6 个域里，产品推荐是唯一已经有真实 POC 验证成果的（ISG SSR），不是纸上谈兵。
2. **它是服务的利润入口**：服务是 SSG 的利润主体，推荐决定服务能不能卖出去，业务意义最直接。
3. **它最适合验证框架**：拿一个已经跑通的域，去验证「交付层 + 引擎层 + ISO 结合点」这套顶层框架能不能落地——跑通了，其他 5 个域照模式复制。

---

## 2. 概念定位：推荐是一个"能力层"，不是"功能点"

**一句话定义**：产品推荐 = 把"SSG 服务专家脑子里的推荐经验"，沉淀成"可规模化、可解释、可追踪的 AI 能力"。

### 业务问题的本质

今天，服务推荐靠销售的个人经验：

- **覆盖不均**：老销售知道"这台 GPU 服务器该配什么服务"，新销售不知道。
- **高质量不稳定**：同一个人，不同时间、不同心情，推荐可能不一样。
- **高价值 attach 漏**：该推的高级服务没推出去，利润悄悄流失。

一句话痛点：**服务是 SSG 的利润主体，但推荐环节"靠人"，是结构性的瓶颈**——它不随团队规模增长，反而随人员流动而流失。

### 在顶层设计里的位置

```
引擎层（能力）        Config & Quote 域 · 产品推荐 sub-agent
        ↓ 调用
交付层（消费）        SSG Sales persona 的推荐工作台
        ↓ 输出
ISO Entry Layer       对 ISO 前台的接口能力
```

本质：不是"多一个工具"，而是"把服务从被动的附加项，变成主动的价值主张"。

**能力层的对外形态 = 顾问（加层，不替代）**：能力层内部是引擎 + 规则 + 逻辑（保持不动），对外表现为「顾问」——能被自然语言问、给 Insight，而非"功能点"。定义它的方式是"**能回答什么、给什么洞察**"，而非"有哪些功能"。这是「能力层而非功能点」的后半句：能力层不但是有内在结构的能力，对外还以对话形态交付。

## 3. 推荐能力层的四个维度

推荐作为一个能力层，要回答四个问题：**推什么、在哪推、怎么推、推多少**。这四个维度决定了它不是一个"功能点"，而是一个有内在结构的"能力"。

### 3.1 在哪推：多环节 + 一致性

推荐不是发生在某一个环节，而是贯穿多个环节：**配置、报价（bid）、续约、RFP 应答……**

核心设计问题：每个环节各自做推荐，必然互相打架（一致性崩）+ 各自冷启动（准确性差）。

答案只有一条：**单一引擎 + 多触达点**。

- 引擎层只有一个推荐引擎（唯一真相源），不是每个环节各写一套。
- 交付层多个触达点都调这同一个引擎。
- **一致性**由"引擎唯一"这个结构保证——同一个客户 + 配置，走到哪个环节都是同一套推荐逻辑，而不是靠"环节间事后对齐"（那永远对不齐）。
- **准确性**靠"引擎统一逻辑 + 各触达点自带上下文（客户状态、环节目标、产品范围）"——逻辑一致、场景适配。

这落到顶层设计的两个既有概念上：**引擎层 vs 交付层分离**（引擎唯一、交付多点）+ **L0 共享上下文**（推荐结果作为共享的 Scores/States 跨环节复用，不重算）。

### 3.2 怎么推：多形态

推荐的交互形态多样，底层共享**同一个引擎 + 同一套产品知识 + 同一套可解释逻辑**，只是触发方式和输出粒度不同：

| 形态 | 触发 | 例子 |
|---|---|---|
| 主动推（Proactive） | 配置/报价时 AI 主动推 | 配置 SR650 时，自动推荐配套的 Premier 支持 |
| 应答 RFP（Request-driven） | 客户发 RFP/询价 | 客户要"3 年数据保护 + NBD"，AI 生成服务方案 |
| 续约/翻新（Renewal） | 合同到期 | 合同到期推续约 + 升级 |
| 交叉/向上（Cross-sell / Upsell） | 存量客户 | 已购基础支持，推高级支持 |
| 问答式（Pull / Q&A） | 销售主动问 | "这个客户该推什么服务" |

关键映射：**确定性触发（主动推/续约）→ workflow；要理解自然语言需求的（应答 RFP）→ agent**。这正是顶层设计"workflow vs agent 区分"的落地实例。

### 3.3 推什么：推荐粒度

推荐对象不是单一粒度，而是分层的：

- **单产品**（type + term + SLA）——配置环节
- **服务组合 / bundle**（基础 + 高级支持 + 数据保护）——报价环节
- **完整方案**（针对客户场景的端到端）——RFP 应答

概念意义：引擎要能输出**不同粒度的推荐**，对应不同环节/形态。这决定了能力层的输出结构——不是"吐一个产品"，而是"按场景吐对应粒度的推荐"。

### 3.4 推多少：克制的推荐

推荐不是越多越好。一个可信的推荐能力，要有"克制"的能力：

- **低置信度** → 不推，或降级为"仅供参考"
- **低价值 / 风险客户** → 克制
- **客户已明确拒绝** → 不重复推

克制是可解释性的姊妹概念：**可解释性回答"为什么推这个"，克制回答"什么时候不该推"**。两者共同构成"销售信得过"的前提——一个敢说"这次我不推"的推荐系统，比一个永远在推的系统更可信。

**克制与 attach 不矛盾（业务逻辑链）**：克制 → 精准 → 销售信任 → 采纳率 ↑ → 高质量 attach ↑。推一堆销售不信的推荐，等于没推，还消耗销售时间；敢说"不推"的系统，销售才信它说的"推"。所以克制的 KPI 是**采纳率**和**attach 质量**，不是推荐数量——这回答了"AI 怎么推得比人还少"的质疑。

## 4. Agent + Workspace 概念

### Agent 概念

产品推荐 sub-agent 的职责 = **理解客户场景 → 匹配服务组合 → 给出可解释的推荐 + 理由**。它在多环节、多形态、多粒度下被调用，但底层是同一个引擎 + 同一套产品知识。

**workflow vs agent 区分**：确定性触发（配置时自动推荐、续约提醒）用 workflow（可预测、低成本）；需理解自然语言需求的（RFP 应答、销售问答）用 agent（灵活、需 guardrail）。

### Workspace 概念

SSG Sales persona 的"推荐工作台"，三个动作构成闭环：

- **看（Data）**：客户画像、装机量、历史购买
- **判断（Insight）**：推荐 + 理由 + 置信度
- **做（效率）**：采纳推荐 → 生成报价

**覆盖度概念**：推荐工作台从 L0（纯人工）走到 L2（AI 建议、人工决策）是现实目标，L3（AI 主导、人工例外）是演进方向。覆盖度是给管理层看的价值证明，比"准确率"好懂。

**可解释性是前提**：因为人要拍板，推荐必须带理由。这是"推荐"区别于"黑箱打分"的分界线。

## 5. 对外的桥：ISO 结合点 + 信任梯度

### 信任梯度

同一推荐结果，三层消费方的信任度和诉求不同：

- **SSG 内部专家**：信任高，能自己判断
- **ISO 前台销售**：信任中，需要更强的可解释 + 明确理由
- **客户**：信任低，需要"价值主张"而非"技术理由"

（已有的 Internal / Customer 双版推荐理由，这里补一个中间的 ISO 前台层。）

**信任是"爬上去"的，不是既定的**：ISO 前台"信任中"不是天然假设——SSG 和 ISO 是两个组织，推荐不准，ISO 会归咎 SSG 的 AI。从低信任走到中信任的路径四步：**可解释（起点）→ 克制（质量）→ 结果反馈（证据）→ 长期验证（累积）**。信任梯度描述的是"目标分层"，达成它靠的是"用结果换信任"。

### ISO 结合点

SSG 作为服务专业能力的提供方，通过 ISO Entry Layer 把"推荐能力"输出给 ISO 前台。

概念意义：让 ISO 前台销售"人人自带 SSG 服务专家的推荐能力"——**不是把 SSG 专家派过去，而是把专家的判断力规模化地输出出去**。

**落地通道（待定）**：ISO 前台是 external，不直接用 SSG workspace。"ISO 版表达""客户版表达"这两层推荐理由，通过什么界面触达（PIN / Sphere / Config AI+ 等 ISO 现有工具的接入方式），不由我们主观决定——**此通道留空，待外部环境设计确定后再补**。

## 6. 域间边界

推荐不是孤岛，它和相邻域有明确的边界与协作：

- **推荐（Config & Quote）说"推这个服务"→ 定价（Pricing）说"多少钱"**
- 推荐依赖硬件配置（Config），硬件一变，推荐要跟着变

这是"6 域 Agent 不是孤岛、需要跨域协作"的最具体实例。而且**推荐和定价两个域都是同一个 owner**，它们的边界和协作，正是顶层设计里 A2A 跨域协作要解决的第一个真实案例。

**协作分工**：推荐负责"推什么"，定价负责"多少钱"，配置负责"什么硬件"。三者通过 A2A 协作——推荐结果作为定价的输入，定价结果反哺推荐的"该不该推"（价格不合适，可能就不推）。

**协作顺序（消除循环依赖）**：推荐先行、价格后置——推荐先出候选，定价再算价格，推荐在价格带内收敛。避免"推荐等定价、定价等推荐"的死锁。

**协作的两种形态（叠加，不替代）**：底层是**数据流**（结构化结果传递，保证确定性）；上层是**顾问叙事**（推荐顾问问定价顾问"这个价推不推得动"，配置顾问说"硬件变了推荐要跟着变"）。数据流是确定性的锚点，顾问叙事是业务理解的表达，二者并存。

## 7. 推荐的生命周期

### 闭环：推荐不是终点

- 采纳了吗？（采纳率）
- 采纳后结果如何？（attach 提升、客户满意度）
- 人的否决 / 修改要**反哺引擎**（feedback loop）

没有这个闭环，推荐是死的，业务价值也无法证明。这呼应顶层设计的"评估门禁 + 价值验证闭环"——推荐能力不是"上线即完成"，而是"上线才开始"。

**闭环的双重价值**：对内**改进引擎**（否决/修改反哺模型）；对外**建立跨组织信任**（ISO 看到"推荐准"的采纳率/attach 证据，才从低信任爬到中信任）。后者是信任梯度从假设变成现实的关键。

### 冷启动与知识新鲜度

- **冷启动**：新客户 / 新产品 / 新 GEO 没历史数据 → 靠规则兜底、专家知识、类比迁移。
- **知识新鲜度**：产品知识（catalog、offering 资格、规则）会变 → 引擎要跟着更新。

这是推荐能力的地基——能力层的价值不仅在于"模型多聪明"，还在于"没数据时靠不靠谱、知识变了能不能跟上"。

**知识与数据的三层结构**（对应顶层设计 §6.3）：冷启动与知识新鲜度，落到「Unified Data & Knowledge」的三层——**L1 infra**（数据湖、知识库、catalog、规则，已有）+ **L2 语义层**（ontology + graph + 语义模型，待建）+ **L3 顾问 Agent**（封装对话+洞察的知识专家，待建）。冷启动靠 L1 的规则兜底 + 专家知识；知识新鲜度靠 L2 的更新机制。L3 顾问不是替代 L1/L2，而是 infra 之上的智能封装。

## 8. 业务意义

### 对 SSG

把专业能力规模化——提升 attach rate 与 coverage，把"人脑经验"沉淀为"可复用能力资产"。专家走了，能力不走。

### 对 ISO

前台销售获得"随身服务顾问"，降低对个人经验的依赖，新人也能推对服务。

### 对整体

支撑 SSG Northstar（Build and operate AI for the Modern Enterprise），是"AI-native 销售组织"的第一个可验证切片。

### 量化锚点（概念层点到为止）

ISG SSR POC 已经证明：AI 推荐的服务组合分布，与客户真实购买的分布高度重合——这为"这个概念已被证明可行"提供了证据。具体数字以 POC 报告为准。

---

## 9. 示范价值

产品推荐不只是一个 agent——它是顶层设计"从抽象到具体"的第一块样板。

它的价值在于：用一个已经跑通的域，验证「交付层 + 引擎层 + ISO 结合点」这套框架能不能跑通。**跑通了，其他 5 个域照这个模式复制；跑不通，问题出在框架而非产品推荐本身。**

这也正是把它作为"第一个示范域"的完整含义：它既是产品推荐自己的设计，也是整个 SSG AI 顶层设计的一次压力测试。
