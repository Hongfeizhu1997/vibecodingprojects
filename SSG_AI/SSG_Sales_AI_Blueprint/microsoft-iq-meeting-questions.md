# 微软 IQ 生态 · 技术问题清单（待与 Leon 会议确认）

> 日期：2026-10-15
> Owner：Hongfei
> 用途：带去与微软 Leon 的会议，针对"服务销售总智能体"设计，确认微软 Work IQ / Fabric IQ / Copilot 的能力边界与落地可行性
> 状态：待会议确认

---

## 背景（一句话）

我们要做一个 **服务销售总智能体**：一个入口串起 opportunity → solution → 初步报价 → 报价 → CPQ 的全流程，拆解出「服务介绍 / 服务推荐 / 服务配置 / 服务+硬件匹配 / 服务支持范围 / 服务报价」等能力。正在评估能否复用微软 Work IQ（工作上下文）+ Fabric IQ（数据语义）+ Copilot（编排入口）这套生态。

---

## A. 能力边界 & 数据接入（决定可行性，最先问）

**Q1. 非 M365 数据源的接入**
Work IQ 的上下文主要是 M365 数据（邮件/会议/文件/聊天），但我们服务销售的上下文在联想内部系统（CPQ / ICP / SPEP / SCFE）。Work IQ 能接这些非 M365 的数据源吗？怎么接？

**Q2. Ontology 的归属与粒度**
Fabric IQ 的 ontology 是微软预置通用，还是企业可自建？我们服务销售的 ontology（服务产品 / 硬件 / 报价 / 客户关系）需要自己建，Fabric IQ 支持到什么粒度？

**Q3. Insight 的可解释性**
Work IQ / Fabric IQ 返回的 Insight，能带"可解释的理由"吗？我们的推荐必须带理由（人拍板的前提），还是理由需要我们的域 Agent 自己生成？

## B. 业务规则 & "克制"

**Q4. 业务规则的承载位置**
我们的推荐有"克制"逻辑（低置信度不推、风险客户克制、已拒不再推），这类规则应该放在 Fabric IQ / Work IQ 里，还是放在我们自己的域 Agent 里？

**Q5. 冷启动与规则兜底**
冷启动场景（新客户 / 新产品没有历史数据，需要靠专家规则兜底）——IQ 是纯数据驱动，还是支持规则兜底？没数据时怎么处理？

## C. 编排确定性（流程 vs 开放任务）

**Q6. 确定性流程编排能力**
服务销售是相对确定的流程（opportunity → solution → 报价 → CPQ），不是开放任务。Copilot 的"自主决定调用哪个专家"，能做确定性的流程编排吗？还是它偏开放任务？

**Q7. 结果确定性与状态连续性**
Agent 间"自然语言对话"协作，结果确定性和状态连续性怎么保证？会不会同样输入给出不同的推荐结果？

## D. 数据主权 & 联想内部平台关系

**Q8. 数据存储与主权**
服务销售数据（报价 / 定价 / 客户）进 Fabric IQ 的 ontology 或 Work IQ 的上下文，数据存在哪里？微软云还是联想内部？合规 / 数据主权怎么保证？

**Q9. 直接操作联想 CPQ**
最终要落到 CPQ，Copilot / Work IQ 的工具调用或 computer use，能直接操作联想 CPQ 吗？还是需要中间层？

**Q10. 与联想内部平台的关系**
联想已有 Vetra / DeerFlow（Agent 编排）、Skill Hub、EKP（知识平台），和 Work IQ / Fabric IQ 是共存还是替代？怎么对接？

## E. 成熟度 & 成本

**Q11. 成熟度**
Work IQ / Fabric IQ 现在的成熟度（preview 还是 GA）？生产环境可用吗？已知限制？

**Q12. 成本模型**
Work IQ 按用量计费，Fabric IQ 怎么算？服务销售高频场景（推荐 / 报价）的成本量级大概多少？

**Q13. 域 Agent 的接入方式**
我们的域 Agent（推荐 / 配置 / 报价）怎么接进 Copilot 生态？用 Copilot Studio 建，还是自建 agent 通过 MCP / A2A 接入？

---

## 优先级提示

- **A 组（Q1–3）+ C 组（Q6–7）最关键**：前三个决定"这事靠不靠得住"，后两个决定"靠得住的前提下能不能落地我们的确定性销售流程"。
- **D 组（Q8–10）**：决定"能不能在联想内部合规落地"，涉及数据主权与平台定位，可能需要 Group IT 参与。
- **B 组（Q4–5）+ E 组（Q11–13）**：决定"落地细节与成本"，可在前两组确认后再细化。
